# 0015 : Gel de la 0.17 et branche `v1`

Statut : acceptée (23 septembre 2026). Portée : tout le dépôt (taille du code, modules du
daemon, versions, branches, CI). Épopée #208, lot A (#209 à #216). Spécification :
`design/v1/gel-et-outillage.md` ; charte : `design/v1/README.md`.

## Contexte

Mesures sur `main` à `fbbf906` (0.17.58) : 212 fichiers Rust, 160 739 lignes ; 42 fichiers
dépassent 1 000 lignes et portent 56 % du workspace, sept dépassent 3 000 (`telegram.rs`
13 716, `dream.rs` 5 859, `agent.rs` 4 192) ; `penelope-daemon` fait 77 548 lignes en 63
modules, 42 de ses fichiers nomment le type `Daemon` et quatre portent un `impl Daemon` ;
25 fonctions dépassent 200 lignes (`command` 1 500, `build_screen` 1 490, `dispatch`
1 155) ; le cœur nomme Telegram 279 fois dans 29 modules du daemon.

Rien n'arrêtait la croissance : `penelope-archtest` vérifie les dépendances entre crates,
les motifs interdits, les cycles et `unsafe`, jamais une taille ; aucun lint de workspace ;
les 71 critères d'acceptation ne sont protégés que par un seuil « au moins 50 » ; aucune
couverture mesurée, aucun scénario rejouable. Chaque lot de correctif ajoutait ses lignes
sans que personne ne le voie.

La V1 (source unique de vérité dans le journal, boucle en pipeline d'étapes typées, daemon
découpé en crates : `design/v1/`) touche les mêmes fichiers que les correctifs quotidiens,
et `main` livre cinq versions par jour en septembre à une instance réelle en service. Le
PRD ne fait plus foi ; ce qui fait foi est le code, `docs/`, les issues et `design/v1/`.

## Décision

1. **La 0.17 est assumée « dirty » et reste en service.** `main` ne reçoit plus que des
   corrections (bug, régression, sécurité) ; toute fonctionnalité et tout module nouveau
   vont dans `v1`.
2. **La dette est gelée mécaniquement, sur `main`, avant toute refonte.** Un fichier
   `crates/penelope-archtest/budget.toml`, lu par `penelope-archtest`, dont les nombres ne
   montent jamais : plafond de 1 000 lignes par fichier source, tests compris (R1), 1 500
   par fichier de tests (R2), liste de référence des fichiers en dépassement qui ne peut
   que rétrécir (R3), plafond de lignes du daemon (R4), liste blanche de ses modules (R5),
   budget d'occurrences de `Daemon` par fichier (R6), `clippy::too_many_lines` à 200 avec
   les allows existants comptés (R7), les 71 `ca_*` figés (R8), relevé de la frontière
   canal/cœur (#214). `UPDATE_BUDGET=1 cargo test -p penelope-archtest` abaisse ; un
   script de CI refuse toute remontée sans le trailer `Dérogation-budget: #N`.
3. **La V1 se refait dans une branche `v1`**, créée depuis `main` après le gel et les
   filets, sur le dernier tag `0.17.x`, les tests inline des sept fichiers géants déjà
   sortis en fichiers frères (#215) pour diviser la surface de conflit. Versions
   `1.0.0-alpha.N`, un bump par lot, **jamais taguées** ; le même `docs/progress.md`, bloc
   « Version 1 » en tête ; fusion `main` → `v1` après chaque release et au moins une fois
   par jour, une fusion en conflit depuis plus de 24 h bloque tout autre lot ; sens
   inverse par cherry-pick `-x`, pour une correction seulement.
4. **Trois gardes de version avant la branche** (#212) : `penelope upgrade` ignore une
   version à suffixe, `release.yml` refuse un tag `v1*` sans la variable de dépôt
   `V1_RELEASES` (absente jusqu'à la bascule), le test `docs` apprend les suffixes. La CI
   tourne sur `v1` ; le job `livraison` reste réservé à `main`.
5. **La bascule** (`v1` devient `main`) se décide sur des critères vérifiables sans
   jugement : CI verte, `budget.toml` vide de tout dépassement, les 71 critères présents,
   migration testée depuis une vraie base 0.17 puis `1.0.0-rc.1` installée explicitement
   sur le poste pendant 24 h, suites réseau au niveau de la ligne de base, test `docs`
   vert, scénarios rejoués sans clé. Borne : six semaines après la création de la
   branche ; au-delà, on arrête et on replanifie.
6. **Chaque tâche des spécifications devient une issue quand son lot démarre**, pas
   avant ; un lot reste un lot au sens de `CLAUDE.md` : code, section, bump. L'état
   d'avancement se lit dans l'épopée #208 ; cette décision ne promet pas de date.

## Raisons

- **1 000 lignes** : 80 % des fichiers tiennent déjà dessous, et 21 des 42 fichiers en
  dépassement y passent rien qu'en déplaçant leurs tests ; DeepSeek Harness tient 855 de
  ses 937 fichiers hôtes sous 500. Le plafond baissera à 800 sur `v1` (tests en fichiers
  frères), pas avant.
- **Un cliquet, pas une discipline** : une règle qui n'est pas mécanique n'est pas tenue ;
  c'est le modèle d'OpenClaw (`max-lines-baseline.txt`, « this list may only shrink »).
  Une entrée périmée est un échec comme les autres, sinon la marge dort.
- **Une branche, pas une refonte en place** : les quatre chantiers touchent les mêmes
  fichiers (`conversation.rs`, `compaction.rs`, `context/`, `agent.rs`, `telegram.rs`) que
  les correctifs quotidiens ; en place, soit les correctifs attendent, soit l'instance
  réelle reçoit du code à moitié restructuré.
- **Jamais de tag sur `v1`** : `parse_version` coupe le suffixe, donc `1.0.0-alpha.1`
  serait vue comme plus récente que `0.17.x` et installée par toutes les instances à leur
  prochaine vérification.
- **La fusion plutôt que le rebase** : branche partagée et longue, un rebase casse toutes
  les copies de travail et les PR ouvertes ; le cherry-pick systématique perd le merge-base
  et re-conflicte à chaque fois (18 à 103 commits par jour sur `main`).

## Conséquences

- Un correctif sur `main` qui fait déborder un fichier de la liste paie ses lignes (un
  test déplacé dans `tests.rs` suffit) ou porte le trailer, visible dans
  `git log --grep=Dérogation-budget` ; attendu 0 à 2 par mois, relus.
- Un module d'urgence sur `main` (sécurité) passe par le trailer et l'édition du budget ;
  le lot suivant sur `v1` reprend la même correction.
- Les tables de données (`build_screen` 1 490 lignes, `all` de `spec.rs` 908,
  `commands.rs`, `templates.rs`) restent dans la liste avec un allow commenté « table » :
  rien ne change tant qu'elles ne grossissent pas.
- CI doublée (9 à 16 min par run, la file macOS est le coût) et fusions de plus en plus
  conflictuelles à mesure que `v1` déplace du code : corrections seules sur `main`, tests
  sortis avant la branche, règle des 24 h, script pour les seize lignes de version, et
  des découpages par déplacements purs (un commit, un déplacement) pour que `git blame`
  survive.
- Un seul `docs/progress.md` à deux blocs : la seule friction humaine attendue. À la
  bascule, le bloc 0.17 part dans `docs/progress-0.17.md`.
- Cette décision précède les lots qu'elle décrit : ce qui est réellement posé se lit dans
  `budget.toml`, `ci.yml` et `release.yml`, pas ici.

## Alternatives écartées

- **Refonte en place, par petits lots sur `main`** : voir les raisons ; et le gel seul
  n'empêche pas les changements de comportement, ce sont les filets du lot B qui les
  attrapent.
- **Un dépôt ou une crate neuve** : on perdrait les 1 775 attributs de test, les 71
  critères, les migrations et le contrat de 320 capacités que la V1 doit conserver à
  l'identique (`design/v1/contrat-fonctionnel.md`).
- **Plafond « 800 lignes hors tests » dès maintenant** : deux comptes à expliquer, et le
  repère « hors tests » dépend d'une heuristique ; 1 000 tests compris, puis 800.
- **`clippy::too_many_lines` à 100** : 92 fonctions au-dessus, autant d'allows seraient un
  bruit ; à 200, la liste nomme exactement les monstres.
- **Un `progress-v1.md` séparé** : il faudrait rendre le test `docs` sensible à la
  branche, l'indexer, adapter l'extraction des notes de release, et fusionner les deux à
  la bascule de toute façon.
- **Les rulesets GitHub comme garantie** : les sessions agissent avec les droits du
  propriétaire ; les gardes sont dans le code et la CI, les rulesets une couche de plus.
- **Une couverture à 100 % par fichier** (DeepSeek Harness) : le code macOS n'est pas
  compilé sur Linux et vingt tests sont ignorés ; un plancher par crate posé sur la mesure
  réelle, à cliquet vers le haut (R9, lot B), est ce qui tient.
